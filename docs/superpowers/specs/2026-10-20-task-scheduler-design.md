- Docker 任务支持选择容器并执行 start、stop、restart。
- 提供中文管理界面、定时调度、手动执行和执行日志。
- 参考本地 `z-media-workflow`，通过 GitHub Actions 构建并推送 Docker Hub，NAS 拉取镜像运行。

## 方案选择

考虑三种实现方式：系统 Cron 配管理界面、应用内调度、独立队列与工作进程。首版选择应用内调度：一个 Go 进程同时提供管理 API、静态页面、调度器及任务执行器，SQLite 保存数据。这个范围不需要多个服务之间协调任务，也方便在 NAS 上部署和升级。

页面使用 Go 嵌入的 HTML、CSS 和 JavaScript，避免额外的前端运行服务。SQLite 采用纯 Go 驱动，避免 Windows 本地测试和 Linux 构建依赖 C 编译器。具体依赖版本在实施计划阶段核对并固定。

首版不实现多主机管理、多实例调度、通用 Shell 脚本、任务依赖、自动通知或 NAS 开关机。服务停止时无法触发任务，不承诺跨进程故障的恰好执行一次。

## 页面与操作流程

首次访问创建管理员账号，之后通过登录进入面板。界面包含任务列表、任务编辑、执行记录及基础设置。

- 列表展示名称、类型、启用状态、调度规则、下次执行时间和最近一次结果。
- 创建任务时选择 curl 或 Docker，配置执行内容、时间规则和超时时间。
- 支持编辑、启用、暂停、立即执行及删除；删除正在执行的任务返回冲突提示。
- 暂停阻止后续定时触发；编辑不改变已经开始的执行快照。
- 执行详情展示触发来源、起止时间、耗时、结果及截断后的输出。
- curl 编辑器直接保存完整命令，不转换成 HTTP 表单。管理员主动编辑时可读取原命令；列表和历史接口不返回原命令。

## 调度规则

支持五字段 Cron、固定间隔和指定时间执行一次。界面明确五字段不含秒，固定间隔最短 60 秒，默认时区 `Asia/Shanghai`。

- Cron 按任务时区计算；固定间隔在启用时从当前时间起算，以计划时间加间隔推进，错过的时间点跳过。
- 单次任务保存明确的执行时刻，自动执行结束后关闭；失败时保留失败记录，不自动循环重试。
- 更新或重新启用任务时重新计算后续执行时间。已过期的单次任务必须改到未来才能重新启用。
- 服务启动时重新加载任务，跳过停机期间错过的触发；过期单次任务标为过期并关闭。
- 同一任务只允许一个执行实例，手动执行也遵守此限制。
- 全局最多同时执行 4 个任务。定时触发遇到容量不足记录跳过，手动执行返回繁忙，不积累无限队列。
- 同一容器的不同 Docker 任务也互斥，避免并发 start、stop 或 restart。
- 默认超时 60 秒，可在 1 至 3600 秒之间调整。
- 首版失败后不自动重试；用户可立即执行重试，避免非幂等请求和 restart 被重复执行。

## curl 执行

镜像包含 curl、CA 证书和时区数据。服务采用支持引号及反斜杠换行的参数解析器，要求命令以 `curl` 开头，然后直接启动 curl 子进程，不调用 Shell。

- 支持常用请求选项，包括请求方法、Header、认证、请求体、重定向和文件上传。
- 管道、命令连接、重定向、变量展开、反引号和命令替换不作为 Shell 语法执行；未加引号的 Shell 操作符在保存时拒绝。引号中的内容作为普通参数保留。
- 路径按容器文件系统解释。使用 `@文件` 上传时，用户需要显式配置额外的数据目录挂载；首版默认只挂载应用数据和 Docker socket。
- 应用超时作为执行上限，超时或服务关闭时终止对应 curl 子进程并等待退出，避免遗留进程。
- 禁用 curl 隐式加载用户默认配置；记录退出码和可取得的 HTTP 状态码，HTTP 4xx/5xx 默认判为失败。
- `--write-out` 由服务用于提取执行元数据，首版不接受用户自定义 `-w` 或 `--write-out`，保存时给出明确提示；其他不兼容参数也必须在保存时反馈，不能静默改变含义。
- 输出重定向到用户指定文件时，执行详情说明响应正文已写入文件。
- 每次执行保存的输出最多 64 KiB，超过后继续排空输出但截断保存，防止内存和数据库失控。

curl 凭据属于管理员私有数据，数据库按受限权限保存；API、普通应用日志和执行记录不暴露原始认证参数。已知密钥应从输出中遮盖，但任意接口响应可能包含未知敏感内容，因此执行记录同样只允许管理员读取。

## Docker 执行

通过 Docker Engine API 连接映射到容器内的 Unix socket，连接路径可配置，默认 `/var/run/docker.sock`。启动时检查连接和 API 版本兼容性，失败时界面显示原因，curl 任务仍可工作。

- 容器选择列表包括运行中和已停止的容器，以容器 ID 保存目标并展示名称。
- 提交前及执行前验证目标存在；目标被删除重建后提示重新选择，不悄悄操作同名新容器。
- start 遇到已运行容器、stop 遇到已停止容器，记录为成功且注明无需操作。
- restart 调用 Docker 的 restart 操作；stop/restart 使用有界的优雅停止等待，并受任务执行超时约束。
- Docker 操作返回成功表示引擎已完成对应请求，不表示容器内业务已健康。
- 默认禁止控制调度器自身。Compose 使用固定名称和识别标签，服务启动时核对自身 ID；无法可靠识别时禁用 Docker 写操作并提示修复。
- API 超时或连接中断时记录结果未知，提示检查容器状态，不自动重发。

挂载 socket 本身具有高权限，因此所有管理操作必须登录，默认不开放 Docker TCP 接口，也不要求 `privileged`。NAS 上真实 socket 路径和卷权限需要部署时验证。

## 数据与模块边界

持久目录统一为 `/app/data`，包含 SQLite 数据库、必要配置和管理员认证数据。任务记录保存调度配置及执行参数；执行历史保存任务名称和执行配置的脱敏快照、触发来源、状态、时间、错误及受限输出。

每次启动将此前未完成的执行记录标为中断，之后只计算未来的调度，不自动重跑。历史默认保留 30 天，在后台定期清理；删除任务保留其已有历史直至过期。

模块分别负责：HTTP/API 与认证、参数校验、SQLite 存储、调度与并发控制、curl 执行、Docker 客户端、内嵌页面。调度器通过统一执行接口调用两类执行器，执行器不直接修改任务调度规则。

管理员密码使用成熟的密码哈希方案存储；登录使用 HttpOnly、SameSite 会话 cookie，写操作校验 CSRF，登录增加尝试次数限制。服务重启后重新登录。未初始化状态仅允许创建第一个管理员，初始化完成后关闭初始化写接口。

## 构建、发布和部署

代码仓库为 `github.com/jiuwusan/z-task-scheduler`。沿用参考项目的 GitHub Actions 发布流程，但测试和构建替换成 Go 工具链。

- push `master`、面向 `master` 的 PR、手动触发工作流。
- 先进行 Go 单元/API 测试和静态检查，再构建 Docker 镜像。
- Dockerfile 分阶段编译 Go，运行阶段只保留应用、curl、证书和时区数据。
- 使用 Docker 官方 Buildx、metadata、login、build-push Actions 和 GitHub 构建缓存。
- 非 PR 构建登录并推送 Docker Hub；PR 只测试和构建，不使用发布凭据或推送。
- `master` 发布 `latest`、`master`、`sha-提交短哈希`；手动运行其他分支只发布分支和提交标签。
- 兼容 `OCKERHUB_USERNAME` 或 `DOCKERHUB_USERNAME`，配合 `DOCKERHUB_TOKEN`。新仓库是否已有这些 Secret 需要单独检查，不能假定自动继承。

Compose 默认镜像 `jiuwusan/z-task-scheduler:latest`，容器名 `z-task-scheduler`，端口建议 `3010:3000`，避免占用参考项目的 3000 端口。默认使用命名卷保存 `/app/data`，允许改为 NAS 共享目录；映射 Docker socket，设置时区、`restart: always`、健康检查、关闭宽限时间和日志轮转。使用普通 Compose 网络，不要求预先创建外部网络；调用其他容器时可使用 NAS 映射端口，或由用户显式加入现有 `wk` 网络。

运行用户需要同时能写数据卷和访问宿主机 socket；Compose 支持添加宿主机 socket 对应组，不把 socket 修改为全员可写，不静默降级为特权容器。引导文档说明如何确认 QNAP 的实际组和权限。

NAS 只需要拉取并启动镜像。开发电脑安装 Go 可执行本地测试和编译；本地 Docker 可用于完整集成验证，但不是远端构建的前提。最终镜像在 Linux CI 中验证 curl 和 Unix socket 行为。

- 参数解析测试覆盖 JSON、单/双引号、反斜杠换行及拒绝 Shell 操作符，保证请求体不变。
